# @canrush/site

Сайт CanRush на Next.js 16. Текущий MVP реализует публичный вход по одноразовой Magic Link, защищённый профиль и пустое состояние будущего избранного.

## Стек

- Next.js App Router, React, TypeScript
- Better Auth 1.7.2, built-in PostgreSQL adapter
- PostgreSQL через `pg`
- Nodemailer и SpaceWeb SMTP
- Vitest, отдельный integration suite для auth

## Что нужно локально

- Node.js 20.9 или новее
- PostgreSQL
- две отдельные БД: `canrush_site_dev` и `canrush_site_test`
- почтовый ящик SpaceWeb с новым уникальным паролем

Пароль, ранее переданный в чате, использовать нельзя. Сначала смените его в панели SpaceWeb. Новый пароль храните только в `.env.local` или secret manager и не отправляйте в сообщения.

## Настройка

```bash
createdb canrush_site_dev
createdb canrush_site_test
cp apps/site/.env.example apps/site/.env.local
openssl rand -base64 32
```

Результат последней команды внесите в `BETTER_AUTH_SECRET` локально. В `SMTP_PASSWORD` укажите только новый пароль после ротации.

Основные переменные:

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL для dev |
| `TEST_DATABASE_URL` | Отдельная PostgreSQL для integration-тестов |
| `BETTER_AUTH_URL` | Origin приложения, локально `http://localhost:3000`, без `/api/auth` |
| `BETTER_AUTH_SECRET` | Секрет не короче 32 высокоэнтропийных байт |
| `SMTP_HOST` | `smtp.spaceweb.ru` |
| `SMTP_PORT` | `465`, implicit TLS |
| `SMTP_USER` | Адрес отправителя и SMTP-логин, они должны совпадать |
| `SMTP_PASSWORD` | Новый пароль ящика |
| `MAIL_FROM_NAME` | Отображаемое имя отправителя |

IMAP, POP3 и Webmail приложению не нужны. Они относятся только к чтению ящика; Magic Link использует SMTP.

## База данных

Сначала посмотреть план без изменений:

```bash
npm -w apps/site run db:plan
```

Применить только отсутствующие versioned migrations:

```bash
npm -w apps/site run db:migrate
```

Migration runner хранит checksum в `_canrush_migrations` и отказывается продолжать, если уже применённый SQL был изменён.

## Запуск

Из корня репозитория:

```bash
npm run dev
```

Откройте `http://localhost:3000`. Без заполненного `.env.local` сервер намеренно завершится с ошибкой конфигурации.

## Проверки

```bash
npm run build
npm run lint
npm test
npm -w apps/site run typecheck
npm -w apps/site run test:auth
```

`test:auth` работает только с `canrush_site_test`, использует уникальные адреса и не выполняет `DROP` или `TRUNCATE`.

Ручной smoke test с новым SMTP-паролем:

1. Запросить ссылку на `/sign-in`.
2. Убедиться, что письмо содержит ссылку на `/auth/confirm`, а не сразу на verifier.
3. Открыть письмо. До нажатия кнопки токен не должен погашаться.
4. Нажать «Войти в CanRush» и увидеть `/profile`.
5. Повторно открыть ссылку и получить безопасную ошибку.
6. Выйти и проверить, что `/profile` снова перенаправляет на вход.

## Реализованные меры безопасности

- токен Better Auth живёт 5 минут, хранится как хэш и атомарно погашается один раз;
- email/password и социальные providers отключены;
- запрос письма проверяет trusted origin и ограничивается по IP и HMAC нормализованного email;
- callback URL фиксированы, Host header не используется при создании ссылки;
- interstitial требует явный POST, поэтому GET-сканер почты не расходует токен;
- session cookie серверная, HttpOnly, SameSite=Lax и Secure на HTTPS;
- CSP с nonce, запрет iframe/object, no-store и no-referrer на чувствительных маршрутах;
- SMTP использует port 465, TLS >= 1.2, проверку сертификата и фиксированный From;
- токены, email и секреты не пишутся в application logs.

Magic Link доказывает доступ к почтовому ящику, но не является phishing-resistant MFA. Для административных или других чувствительных действий позже нужны passkeys/WebAuthn либо повторная проверка.

## Перед публичным запуском

На 5 сентября 2026 года авторитетные DNS-серверы `canrush.ru` не возвращают MX, SPF, DKIM и DMARC. Настройте и повторно проверьте:

- MX: `mx1.spaceweb.ru.` priority 10;
- MX: `mx2.spaceweb.ru.` priority 20;
- SPF: `v=spf1 include:_spf.spaceweb.ru ~all`;
- DKIM: включить в панели SpaceWeb и проверить опубликованный selector;
- DMARC: начать с `v=DMARC1; p=none; aspf=r; sp=none`, затем ужесточать после проверки alignment и отчётов.

Также до публикации нужны managed PostgreSQL и логи на территории РФ, TLS и least-privilege роль БД, резервные копии, финальная политика обработки данных, согласие/основание обработки, удаление аккаунта и юридическая проверка требований 152-ФЗ. При злоупотреблении добавьте CAPTCHA/WAF поверх уже действующих лимитов.

## Фотографии отзывов

Перед запуском версии с фотографиями выполните `npm -w apps/site run db:plan`,
затем `npm -w apps/site run db:migrate` (миграция `0006_review_photos.sql`).
Изображения и небольшие превью хранятся в PostgreSQL в `reviewPhoto`; они входят
в резервную копию базы и удаляются каскадно с отзывом или аккаунтом.

Один отзыв содержит до пяти JPG/PNG/WebP по 5 МиБ. Сервер проверяет реальный
формат, запрещает анимацию, ограничивает декодирование 40 мегапикселями,
нормализует ориентацию и перекодирует в WebP до 2048 px без EXIF/GPS.
Каждый сохранённый файл ограничен 2 МиБ, превью — 256 КиБ.
Публичный маршрут `/api/review-photos/[id]` отдаёт только сохранённый WebP без
долгого кэширования, чтобы удалённые фото сразу перестали обслуживаться сервером.

Лимиты тела запроса Next Server Actions и Proxy — 26 МиБ. Внешний reverse proxy
также должен пропускать запросы этого размера (для Nginx: `client_max_body_size 26m;`).
Если внешний прокси настроен строже, форма сохранит выбранные файлы и покажет
ошибку отправки; можно повторить загрузку после исправления настройки.

## Социальный профиль

Перед запуском обновлённого профиля выполните `npm -w apps/site run db:plan`,
затем `npm -w apps/site run db:migrate` (`0007_profile_community.sql` и
`0008_profile_customization.sql`).
Подписки, полученные достижения, выбранные теги, комментарии и настройки
присутствия хранятся в PostgreSQL; связанные данные удаляются вместе с аккаунтом.

- Друзья — только взаимные подписчики. Отписка убирает дружбу, но сохраняет
  обратную подписку. Списки доступны в `/profile/[username]/connections`.
- Можно выбрать один полученный тег или оставить профиль без тега. Условия и названия
  заданы в `src/lib/profile-achievements.ts`. Достижения начисляются по реальным
  отзывам, избранному, опубликованным тирлистам и взаимным подпискам, а также
  ретроактивно при открытии профиля. Полученные теги не отзываются при удалении
  контента или отписке. Исключение: «Админ» доступен только действующему
  администратору и сразу скрывается при отзыве прав. Тег показывается рядом
  с ником во всех отзывах, включая ранее опубликованные.
- Статистика показывает средние дизайн/вкус/состав и общую среднюю оценку.
  Для гистограммы среднее трёх критериев каждого отзыва округляется до целого.
- На стене доступны комментарии до 1000 символов, по 20 на страницу.
  Один автор может публиковать не чаще раза в 30 секунд (атомарный лимит в БД).
  Автор и владелец стены могут удалить комментарий; заблокированный аккаунт
  не может публиковать комментарии и оформлять подписки.
- Присутствие обновляется в видимой вкладке при активности пользователя;
  неактивная вкладка прекращает heartbeat спустя 90 секунд без взаимодействий.
  «В сети» означает heartbeat не старше двух минут и действующую сессию.
  Профиль обновляет индикатор раз в 30 секунд. Владелец может скрыть статус;
  скрытый профиль не записывает время активности. Точное время посещения
  публично не возвращается.

Интеграционные проверки входят в `npm -w apps/site run test:auth` и используют
только `canrush_site_test`. Примените миграцию и к этой отдельной базе.

### Аватар и баннер

В `/profile/edit` можно загрузить, заменить или удалить собственные изображения.
Поддерживаются статичные JPG/PNG/WebP до 5 МиБ и 40 мегапикселей. Сервер
декодирует фактическое содержимое, нормализует ориентацию, удаляет метаданные
и сохраняет WebP: аватар 512×512, баннер в пределах 1920×1080. Готовый файл
не превышает 2 МиБ. Область кадрирования выбирается в редакторе; для старых клиентов без координат используется центральная обрезка аватара.

Поля профиля и изображения сохраняются одной транзакцией. Ошибка юзернейма
не удаляет старые изображения. `profileImage` хранит по одному файлу каждого
типа и входит в резервную копию PostgreSQL. При замене меняется ID файла;
старый URL перестаёт работать. `/api/profile-images/[id]` отдаёт только WebP
с `no-store`; удаление аккаунта каскадно удаляет изображения.

Избранное доступно через карточку в профиле. В хедере и таб-баре осталось
четыре раздела: каталог, цены, тирлисты, профиль.

### Опыт и рейтинг

Миграции `0009_profile_experience.sql` и `0010_experience_concurrency.sql` добавляют журнал XP и рейтинг. Начисления выполняются триггерами в одной транзакции с действием: новый отзыв о напитке +25 XP, первые 20 разных напитков в избранном +2 XP, первые 10 опубликованных тирлистов +50 XP, каждое достижение (кроме роли администратора) +20 XP. Старые записи учитываются при миграции. Удаление, повторное добавление и редактирование не обнуляют ключ начисления; лимиты пожизненные. Комментарии, подписки и онлайн сами по себе XP не дают. Блокированные аккаунты исключаются из рейтинга и не получают новых начислений.

Уровень 1 начинается с 0 XP, следующие пороги — 100, 300, 600, 1000 XP (`50 × уровень × (уровень − 1)`). При равном XP место общее. `/leaderboard` показывает первые 100 участников; профиль показывает собственное место. Уровни рядом с тегом в профиле, отзывах и на стене обновляются каждые 30 секунд на видимой вкладке одним пакетным запросом для авторов страницы.

Редактор изображений поддерживает drag & drop на аватар и баннер и модальное кадрирование (аватар 1:1, баннер 4:1): перемещение пальцем/мышью, масштаб и доступные с клавиатуры ползунки. Выбранная область проверяется на сервере после нормализации EXIF. Сохранённый баннер сохраняет пропорции 4:1 на всех экранах. «Изменить кадр» повторно открывает исходный файл до сохранения; после сохранения работает с сохранённым изображением.

### Города и местоположение

В хедере доступен поиск по 16 городам и кнопка геолокации браузера. Координаты обрабатываются только на устройстве, на сервер передаётся выбранный идентификатор города. Предлагается ближайший поддерживаемый город в радиусе 60 км при точности до 30 км, затем пользователь подтверждает выбор. При отказе, таймауте или вне зоны покрытия доступен ручной выбор. Геолокация требует HTTPS (localhost разрешён браузером).

Выбор хранится год в cookie `canrush-city` (HttpOnly, SameSite=Lax, Secure в production); без выбора используется Москва. Каталог, страницы напитков и сравнение цен читают только выбранный регион. Отсутствие файла/предложений не подменяется другим городом. Для старого московского среза допустимы только предложения Едадила с московским URL. Отзывы и тирлисты общие; избранный напиток без местных предложений остаётся в профиле.

Срезы `data/regions/<city>.json` загружаются с кэшированием распарсенного содержимого по имени, inode, mtime и размеру файла; публикация парсером атомарна. Кэш одного города не используется другим. Просроченные акции исключаются даже до очередного запуска парсера. Изображения общие для всех городов и отдаются с длительным immutable-кэшем. Обновление выбора города не вызывает загрузку новых данных с сайтов магазинов.

После обновления кода выполните из корня `npm run parse -- --cities=all --source=edadeal`. Docker volumes `catalog-data`, `product-images`, `parser-data` сохраняют региональные срезы и кэш между перезапусками; дополнительных сервисов или ключей геокодера не требуется.

### Составы при развёртывании

Срез составов с проверенными привязками к вариантам напитков хранится в `src/content/ingredients.json` и включается в сборку сайта. Это данные источников, а не подтверждение рецептуры по этикетке; рынок и дата получения показываются в карточке. Если `data/ingredients.json` в общем volume отсутствует, сайт использует этот встроенный срез. Если файл в volume существует, он остаётся приоритетным, включая явное отсутствие записи. Повреждённый файл не подменяется незаметно старым срезом. Переносить файл вручную для нового развёртывания не нужно.

После сбора и проверки привязок встроенный срез обновляется из корня командой `npm -w apps/parser run ingredients:publish -- --bundled`. Состав подбирается по точной паре бренд/вкус: наличие данных у Tropical не означает наличие данных у Original или Sugarfree.

### Выпадающий список тегов

В профиле список достижений раскрывается по нажатию на поле тега. Поиск работает по названию и условию получения; закрытые теги показывают прогресс, но недоступны для выбора. Одновременно выбирается один тег, изменение подтверждается кнопкой «Сохранить тег». Административный пункт и счётчик доступных достижений учитывают роль смотрящего: обычному пользователю этот пункт не показывается.

Миграция `0011_telegram_achievement.sql` добавляет тег «Я в телеге». Он выдаётся за корректно заполненное поле Telegram в профиле, не подтверждает владение аккаунтом и даёт 20 XP один раз. Как и другие достижения, он сохраняется после выполнения условия: удаление или смена ссылки не удаляет достижение и не начисляет опыт повторно. Существующие ссылки учитываются при миграции. На VPS после обновления образа выполните `db:plan`, затем миграцию через `node apps/site/scripts/migrate.mjs` внутри контейнера `site`.

### Дашборд администрирования

`/admin` открывает аналитику; вкладки хранятся в `?tab=analytics|users|tierlists|reviews|wall|admins`. Таблицы ищут по текущему разделу, показывают по 25 записей и сохраняют вкладку, поиск и страницу после действий. Доступ проверяется сервером, действия модерации записываются в `adminAuditLog`. Комментарии стены удаляются администратором в той же транзакции, что и запись аудита.

Аналитика использует полные счётчики БД: участников, отзывов, тирлистов, комментариев, администраторов и уникальных пользователей с действующей сессией. Последний показатель не равен числу людей онлайн. Дополнительно показываются прирост за 30 дней, регистрации за 14 календарных дней по Москве, статусы тирлистов, блокировки и средняя оценка отзывов. Метрики обновляются при открытии страницы, внешняя аналитика посещений не подключается.

Сортировка каталога «По рейтингу» упорядочивает весь результат до пагинации: сначала средняя оценка, затем количество отзывов, затем цена. Напитки без оценок и с неуточнённым вкусом идут после оценённых.

### Переход отзывов на шкалу 1–10 (миграция 0012)

Оценки дизайна и вкуса умножаются на 2 (4/5 → 8/10). Общая оценка теперь равна `(дизайн + вкус) / 2`; состав больше не учитывается. Информационный раздел состава напитка сохраняется. Миграция не меняет ID, автора, текст, фотографии, даты и опыт. Исходные оценки сохраняются в `review.legacyRatings` (шкала 5), старый `composition` остаётся архивным и допускает NULL для новых отзывов. Редактирование отзыва не перезаписывает архив. Миграция и запись в журнал выполняются в одной транзакции; повторный `db:migrate` не удваивает оценки повторно.

Обновление VPS требует миграции **до запуска новой версии** и остановки старой версии на время перехода. Сначала соберите образ и проверьте план. Сохраните резервную копию БД; при ошибке не продолжайте следующие команды.

```bash
(
set -eu
umask 077
cd /opt/canrush
git pull origin main
docker compose build site
docker compose run --rm --no-deps site node apps/site/scripts/migrate.mjs --plan
docker compose stop site
mkdir -p /opt/canrush-backups
chmod 700 /opt/canrush-backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "/opt/canrush-backups/before-ratings-$(date +%Y%m%d-%H%M%S).dump"
docker compose run --rm --no-deps site node apps/site/scripts/migrate.mjs
docker compose up -d site
)
```
