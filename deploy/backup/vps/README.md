# Резервные копии на резервный VPS

Вторая, работающая схема бэкапов (первая — Яндекс Диск через rclone, `../README.md`; её systemd-таймер на сервере
выключен). Схема: основной VPS (`ru-vps`) каждую ночь делает копию, резервный зарубежный VPS (`backup-vps`) её забирает.

| Где | Что | Когда (по Москве) |
| --- | --- | --- |
| Основной VPS | `backup.sh`: `pg_dump` базы сайта (custom format, проверка `pg_restore --list`) + `/opt/canrush/.env`, tar, шифрование `age` на открытый SSH-ключ владельца (`recipients.txt`). Хранит 3 последние копии в `/var/backups/canrush` | 03:30 (`/etc/cron.d/canrush-backup`) |
| Резервный VPS | `pull.sh`: забирает новую копию, сверяет sha256, `prune.py` оставляет 7 ежедневных, 4 еженедельных и 6 ежемесячных копий в `/var/backups/canrush` | 05:00 (`/etc/cron.d/canrush-backup`) |

- Скрипты лежат в `/opt/canrush-backup` на обоих серверах (копии — в этой папке `deploy/backup/vps`; меняя скрипт,
  копируй его на сервер).
- Копии зашифрованы: прочитать их может только закрытый ключ владельца (`~/.ssh/id_ed25519` на его Mac). Без этого
  ключа копии бесполезны — храни его ещё и в менеджере паролей.
- Резервный VPS заходит на основной своим ключом (`/root/.ssh/canrush_backup`), которому в `authorized_keys` основного
  сервера разрешена только команда `serve.sh`: `list` и `get <файл>`. Ни shell, ни удаления — взлом резервного VPS
  не даёт доступа к продакшену, а взлом основного не стирает копии на резервном.
- Сбои приходят владельцу в Telegram через бота (`notify.sh`, токен и chat id — в `notify.env`, только root): основной
  сервер — если копия не сделана, резервный — если не забрана или последней копии больше 30 часов.
- Персональные данные за рубежом — трансграничная передача (152-ФЗ, ст. 12): нужно уведомление в Роскомнадзор.

## Восстановление

Расшифровать на Mac владельца (нужен `age`: `brew install age`) и развернуть:

```bash
age -d -i ~/.ssh/id_ed25519 -o copy.tar canrush-YYYY-MM-DDTHHMMZ.tar.age
tar -xf copy.tar            # canrush.dump и env (переменные окружения сайта)
```

База прода — Postgres 16 в Alpine (`postgres:16-alpine`), строки там сравниваются побайтно. Восстанавливай в такой же
образ или в базу с сортировкой `C` — иначе таблица `profileCompatibilitySnapshot` (проверка `userLow < userHigh`) не
загрузится:

```bash
createdb --template=template0 --lc-collate=C --lc-ctype=C canrush_restore
pg_restore --no-owner --no-privileges -d canrush_restore canrush.dump
```

Проверено 29 октября 2026: копия расшифровалась, все таблицы загрузились без ошибок, числа строк совпали с продом.
