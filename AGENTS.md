# AGENTS.md — canrush.ru

Monorepo: парсер цен на энергетические напитки (РФ) + сайт.
npm workspaces, TypeScript, Next.js, Playwright, vitest.

## Структура

```
packages/shared/   # общие типы (Product, SourceName, конфиги) — собирается в dist/
apps/parser/       # парсер цен (Playwright + HTTP + фиды)
apps/site/         # Next.js сайт + Better Auth Magic Link + PostgreSQL
data/              # выходные данные парсера (latest.json, raw/, history/, state.json)
```

## Источники и адаптеры

`apps/parser/src/adapters/`:

| Источник     | Файл            | Стратегия                                   |
| ------------ | --------------- | ------------------------------------------- |
| Wildberries  | `wildberries.ts`| `intercept` (перехват JSON API)             |
| Ozon         | `ozon.ts`       | `feed` (партнёрский XML, `OZON_FEED_URL`) → `intercept` |
| Пятёрочка    | `pyaterochka.ts`| `in_page_fetch` (fetch внутри страницы)     |
| Магнит       | `magnit.ts`     | `in_page_fetch` (нужны `storeCode`, `categoryId`) |
| Лента        | `lenta.ts`      | `in_page_fetch`                             |
| Едадил       | `edadeal.ts`    | `http_api` (открытый JSON `search.edadeal.io`, без браузера; только акции; `regionId` = Yandex geoid) |
| Яндекс Лавка | `lavka.ts`      | `http_api` (SSR-страница каталога большой лавки + cookie `lastGeoCoordinate`; полный прайс; города — `sources.lavka.cities`) |

Пищевая ценность (таурин, кофеин, КБЖУ): `npm -w apps/parser run ingredients:nutrition` → GigaChat
(`src/ingredients/gigachat.ts`, `nutrition.ts`) переносит числа из сохранённой страницы состава. Модели не доверяем:
`verifyNutrition` оставляет только число, стоящее вплотную к своей подписи в тексте, и в допустимом диапазоне
(`NUTRITION_RANGES` в `@canrush/shared`). Не ослабляй эту проверку и не проси модель «знать» состав без текста источника.
Ключ — `GIGACHAT_AUTH_KEY` в `apps/parser/.env`, сертификат Минцифры — только для запросов к GigaChat
(`certs/russian_trusted_root_ca.pem`). Блок «Пищевая ценность» на сайте временно скрыт (`SHOW_NUTRITION` в
`catalog-product-ingredients.tsx`): числа хранятся, но показываются только после ручной сверки — источник Red Bull
Original давал 250 мг таурина вместо 400.
Временно (до ручной сверки) составы и КБЖУ товаров без проверенной привязки берутся из карточек Лавки:
`npm -w apps/parser run ingredients:lavka` (`src/ingredients/lavka.ts`) → `status: unverified`, `nutrition.method: 'store'`.
«Краткий состав» Лавки сделан ИИ — не используй его; GigaChat для Лавки не нужен.
Последний вариант — `ingredients:ai`: GigaChat по памяти → `status: ai_generated` (без `sourceUrl`, с `model`), на сайте
плашка «Сгенерировано ИИ». Публикуется только перечень: числа модели (`method: 'ai'`) были шаблонными — не возвращай их без нового контроля. Записи с источником не могут нести `method: 'ai'` или `model`
(`isPublishedIngredients`). Перед массовым прогоном запускай `--control`: в октябре 2026 числа совпадали плохо.

Оптовые поставщики — отдельный поток для кабинета бизнеса, не розничный каталог: `npm -w apps/parser run wholesale`
(`src/wholesale/run.ts`, адаптеры рядом, список — `WHOLESALE_SOURCES` в `@canrush/shared`, JSON из страниц читает `readJsonValue` в `json-scan.ts`; `--source=napolke,otlichnye` — выборочно) пишет
`apps/site/data/wholesale.json` (`WholesaleFile`: цена за банку у самого дешёвого поставщика, кратность упаковки,
поставщик, их число, минимальный заказ, НДС, дата прайса). Бренд, вкус и объём — розничной нормализацией
(`normalizeIdentity` в `normalize.ts`), страна в названии («Red Bull Австрия») вырезается перед ней (`identityTitle`).
Источник, который упал, оставляет прошлые цены как `stale`. Плановый прогон (`schedule.ts`) запускает опт после
обычного. Не подмешивай оптовые цены в `latest.json`/`catalog.json`.

| Оптовый источник | Файл | Стратегия |
| ---------------- | ---- | --------- |
| НаПолке (napolke.ru) | `wholesale/napolke.ts` | `http_api`: HTML категории энергетиков, товары — в RSC-данных Next (`self.__next_f.push`, `productsResponse`), 60 на страницу через `?offset=`, пауза 3–4,5 с; цены для Москвы (адрес сайта по умолчанию). robots.txt разрешает страницы категории, но не срезы по фильтрам — фильтров не передаём. Выдача пересортировывается при листании: дубли убираются по `uuid`, часть товаров за прогон может не попасть. |
| Отличные цены (otlichnye-tseny.ru) | `wholesale/otlichnye.ts` | `http_api`: сайт на Tilda, сам продаёт коробками (Москва и СПб). Сетка каталога грузится API Tilda (`store.tildaapi.com`), его robots.txt закрывает всё — туда не ходим. Ссылки на товары — из `sitemap-store.xml` магазина (раздел `energeticheskiye-napitkki`), цена и «N шт в упаковке · в наличии» — из `product = {…}` страницы товара, пауза 2,5–4 с (~100 страниц, несколько минут). Нет в наличии — пропускаем; минимального заказа на сайте нет. |
| E-sweets (msk.e-sweets.ru) | `wholesale/esweets.ts` | `http_api`: Webasyst, Москва. `/search/`, сортировки и фильтры закрыты в robots.txt — читаем страницу раздела `/category/energeticheskie-napitki/` (24 на страницу, `?page=N`, пауза 3–4,5 с): id, название, «N руб. за шт.», «В упаковке: N шт.», наличие. Блок «Хиты» повторяет карточки — по одной на id. Товары «Нет в наличии» остаются с `inStock: false`: кабинет пишет «нет в наличии» и не сравнивает их в «Дешевле всего». |

Антибот: `src/browser/challenge.ts` (детект), `src/browser/session.ts`
(переиспользование сессий в `.sessions/<source>/`). Разблокировка —
`npm run session:unlock -- --source=<name>` (см. `apps/parser/README.md`).

## Команды (из корня)

```bash
npm install
npx playwright install chromium

npm run dev          # Next.js сайт на http://localhost:3000
npm run build        # сборка всех workspaces (shared → parser/site)
npm run lint         # flat ESLint для parser/shared/site
npm test             # unit-тесты всех workspaces
npm run parse        # однократный прогон парсера
npm run parse -- --source=ozon,wildberries
npm run schedule     # планировщик (CRON_SCHEDULE из .env, по умолч. 0 6 * * * Europe/Moscow)
```

Команды парсера также доступны через workspace:
`npm -w apps/parser run doctor`, `npm -w apps/parser run session:unlock -- --source=...`.

Команды сайта:
`npm -w apps/site run typecheck`, `npm -w apps/site run db:plan`,
`npm -w apps/site run db:migrate`, `npm -w apps/site run test:auth`.

## Важно для агентов

- **Сборка зависит от порядка**: `@canrush/shared` собирается в `dist/` первым
  (через `npm run build --workspaces`); `apps/parser` импортирует типы из
  `@canrush/shared` через `references` в `tsconfig.json`. Перед `npm run parse`
  убедись, что `packages/shared/dist` существует (`npm run build`).
- **ESM + NodeNext**: импорты локальных файлов обязаны иметь расширение `.js`
  (например `from './storage.js'`). Импорты из `@canrush/shared` — без расширения.
- **`noUncheckedIndexedAccess: true`**: результат индексного доступа (`arr[i]`,
  `map.get(k)`) считается `T | undefined` — обрабатывай undefined явно.
- **Next.js site**: `apps/site/tsconfig.json` намеренно использует `module: ESNext`
  и `moduleResolution: Bundler`; правило расширений `.js` из NodeNext к нему не
  применяется. Корневой `npm run dev` запускает этот workspace.
- **Данные каталога сайта**: `saveLatest` синхронизирует группы в игнорируемый
  `apps/site/data/catalog.json`. После парсинга запускай `npm -w apps/parser run
  download-images`, чтобы локализовать изображения и обновить этот срез.
- **Magic Link invariants**: токен живёт 15 минут, хранится как хэш и погашается
  один раз. Email-ссылка ведёт на GET interstitial, а вход выполняется только
  автоматическим POST через Server Action. Action вызывает встроенный `magicLinkVerify`
  и переносит его `Set-Cookie` через Next `cookies()`; не редиректь Action на
  внутренний verifier, иначе Next RSC потеряет cookie. Не возвращай verifier в
  письмо, не делай callback URL пользовательским и не отключай origin checks.
  Вход «Бизнес» несёт в письме только флаг `for=business` (не адрес): `sendMagicLink` узнаёт его по `callbackURL`
  запроса (`audienceFromVerifyUrl` — только точное `/business/cabinet`), письмо уходит через тот же SMTP от
  «<MAIL_FROM_NAME> для бизнеса» с текстом про кабинет, а Action выбирает страницу из `AUDIENCE_DESTINATION`
  (`/profile` или `/business/cabinet`) — `safeRedirectPath` пропускает только их и `/auth/error`.
- **Auth anti-abuse**: запрос письма ограничен database rate limit по IP и HMAC
  нормализованного email. Не сохраняй raw email в ключе лимитера и не переноси
  запрос отправки на server-side `auth.api`, иначе встроенный IP limit обходится.
- **Site secrets**: `DATABASE_URL`, `BETTER_AUTH_SECRET` и SMTP-реквизиты только
  в `apps/site/.env.local`/secret manager. `SMTP_USER` обязан совпадать с From,
  SpaceWeb использует implicit TLS на 465. Не используй раскрытый старый пароль.
- **Миграции сайта**: SQL хранится в `apps/site/migrations/`, checksum — в
  `_canrush_migrations`. Сначала запускай `db:plan`; integration-тесты используют
  только отдельную `canrush_site_test` и не должны делать `DROP`/`TRUNCATE`.
- **Figma**: auth/profile адаптированы из узлов `454:2493` и `465:2035`; точные
  assets находятся в `apps/site/public/brand`, PP Object Sans — в
  `apps/site/fonts`, токены — в `DESIGN.md`. Не подменяй логотипы и не добавляй
  runtime-ссылки на временные Figma assets.
- **Навигация сайта**: `ProfileNavigation` рендерит кнопки хедера (≥960px) и
  таб бар `SiteTabBar` (<960px), иконки общие (`navigation-icon.tsx`). В хедере два
  выпадающих меню `HeaderMenu` — «Сообщество» (Тирлисты, Объявления, Лента, Новости → `/news`, Дейтинг → `/community?type=dating`, иконка `dating`, Люди → `/community?type=people`, иконка `people`, Рейтинг → `/leaderboard`, иконка `leaderboard` — кубок; страница рейтинга передаёт `active="community"`) и «Магазины»
  (Каталог, Цены, Найти → `/market/stores`), за ними отдельная ссылка «Для бизнеса» (`/business`, иконка-портфель `business`, только в хедере ≥960 px и в футере). Свой профиль — аватарка в правом углу хедера на всех ширинах
  (`HeaderProfile`, после колокольчика и настроек, `order: 10`; гостю — синяя кнопка «Войти», уже 420 px — только иконка, чтобы не резать город). Картинку даёт
  `/api/me/avatar` — редирект на сохранённую аватарку, так хедеру не нужен запрос к БД при рендере; без аватарки — иконка. Подпись группы — ссылка на её первую
  страницу (`/tierlists`, `/catalog`), меню открывается наведением или кнопкой-стрелкой рядом. Таб бар — пять
  вкладок: Главная, «Трекер» (`/calendar` — сразу свой трекер выпитого, тот же `DrinkCalendarScreen`, что у `/profile/<ник>/calendar`, но с `tab`: без кнопки «В профиль», листание месяцев остаётся на `/calendar`; гостю — вход; без редиректа, чтобы приложение не показывало пустой тёмный экран между двумя запросами), «Поиск» (`/search`, круглая
  кнопка по центру), «Сообщество» (`/community`) и «Новости» (`/news`, статьи участников); профиля в таб баре
  нет — он в хедере. Вход определяется по наличию cookie сессии (`getSessionCookie`) в `ProfileNavigation`, поэтому
  она async; в тестах передавай `signedIn`. Каталог, цены, магазины и маркет подсвечивают «Поиск», тирлисты и лента —
  «Сообщество», свой трекер — «Трекер».
  Страницы `/market/stores*` передают `active="stores"`: в меню отмечается «Найти». Таб бар
  фиксирован снизу и задаёт `--site-tab-bar-offset` на `html` только там, где он
  есть (юридические страницы и админка без `ProfileNavigation` его не показывают).
  Новые фиксированные снизу элементы и нижние отступы считай через
  `calc(var(--site-tab-bar-offset, 0px) + …)`, иначе таб бар их перекроет.
- **Тесты**: vitest, файлы `apps/parser/test/*.test.ts`. `tsconfig.json` парсера
  включает только `src` — тесты компилируются vitest'ом на лету, не падают в
  `dist`. Не добавляй `test/` в `include` tsconfig (это ломает `rootDir`/`outDir`).
- **Регулярки с кириллицей**: не используй `\b` рядом с кириллическими буквами
  без флага `u` — JS считает word-границу только по ASCII. См. `extractVolumeMl`
  в `apps/parser/src/normalize.ts` (используется `(?![a-zа-яё])`).
- **Не коммить**: `.sessions/`, `data/raw/`, `data/history/`, `data/latest.json`,
  `data/state.json`, `apps/site/data/`, `apps/site/public/images/`, `.env` (см. `.gitignore`).
- **Робототехника**: `src/robots.ts` уважает `robots.txt`. Не отключай его.
- **Поиск по брендам**: русские и другие «как пишут» написания — в `BRAND_SEARCH_ALIASES` (`apps/site/src/lib/search-aliases.ts`), плюс автотранслитерация в обе стороны. Не добавляй их в `ENERGY_DRINK_BRAND_ALIASES`: по ним парсер определяет бренд в названиях товаров. Новый бренд с неочевидным чтением («Juster» → «Джастер») — сразу в поисковый словарь.
- **Едадил — агрегатор**: `source: 'edadeal'`, а сеть (Пятёрочка/Магнит/…) — в
  `Product.retailer`; цены только акционные (`promoEndsAt`). Это единственный
  источник без Playwright — не добавляй ему браузерных стратегий и не ходи на
  запрещённые в `robots.txt` страницы `edadeal.ru` (поиск, `/offers/*`). Полная
  выдача собирается через брендовые батчи (обычный ответ обрезан до 600 групп),
  бренд — по `brandUuid`, затем через глобальные `brandAliases`. Не убирай паузу
  800 мс между запросами.
- **Яндекс Лавка**: только «большая лавка» (`/supermarket/…`, `depotType=supermarket`),
  её нет за пределами Москвы и Петербурга — «лавку у дома» и демо-каталог адаптер
  отбрасывает (`hasSupermarket`). Данные — из SSR `storedehydratedstate-data`, товары
  только из подразделов «Энергетики…» (в категории `energy_beer` есть пиво и вино).
  `/api/` запрещён в robots.txt — не ходи туда и не включай перехват XHR; headless
  получает 403, капчу не обходим. Лавка опрашивается в региональном прогоне рядом с
  Едадилом, её сбой оставляет прошлые цены Лавки как stale (`fetchLavka` в `regions.ts`). На капчу/запрет (`SourceBlockedError`) — ровно один повтор через 60–90 с: с сервера капча бывает разовой; больше повторов не добавляй.
- **Обложки архива**: если картинку не удалось скачать в прогоне, у группы остаётся ссылка CDN Едадила, и с ней карточка уходит в `product-registry.json`. `localizeArchivedCovers` (конец регионального прогона и `download-images`) докачивает такие обложки, повторы после ошибки — не чаще раза в час (`image-cache`). Ссылки CDN протухают, а превью коллекций и магазинов показывают только локальные обложки.
- **Иконки сетей**: адаптер Едадила кладёт логотип сети (`partner.imageUrl`) в
  `Product.retailerIconUrl`. `npm -w apps/parser run download-icons` скачивает
  его в `apps/site/public/images/retailers/` (общий volume с сайтом) и пишет в
  `apps/site/data/retailer-icons.json` запись `{ src, tile }`; favicon по домену —
  только запасной вариант. Логотипы принимаются лишь с `https://leonardo.edadeal.io`.
  Сайт показывает `tile` на всю плашку, ручные иконки из `public/brand/retailers`
  имеют приоритет. Запускай после парсинга вместе с `download-images`.
- **Антибот/блокировки — это норма**: источники часто возвращают 403/498/капчу.
  Не пытайся «обойти» защиту агрессивнее — используй `session:unlock` и
  stale-фоллбэк (`mergeResults` в `storage.ts`). Не увеличивай частоту запросов
  сверх разумного (базовая задержка 3с + джиттер в `run.ts`).
- **Безопасность**: не логируй и не коммить токены (`TG_BOT_TOKEN`, `OZON_FEED_URL`
  с ключами). Секреты — только в `.env`/`.env.local`, которые в `.gitignore`.

## Android-приложение

- `apps/android` — оболочка Capacitor 8 (`ru.canrush.app`, ID после публикации не меняется). WebView грузит живой `https://canrush.ru` (`server.url`), статической сборки сайта нет: SSR, Server Actions и cookie Better Auth работают как в браузере, CSP и origin checks не трогай ради приложения. Публикация — сначала RuStore, Google Play позже. Подробности — `apps/android/README.md`.
- У workspace нет скриптов `build`/`test`/`lint`: корневые команды не требуют Java и Android SDK. Сборка — `npm -w apps/android run apk:debug`.
- `capacitor.config.ts` — источник правды, `android/app/src/main/assets/capacitor.config.json` генерируется `sync`. Иконки и заставка — `npm -w apps/android run icons` из `apps/site/src/app/icon.svg`, не правь PNG руками.
- App Links: intent-filter `canrush.ru` с `autoVerify`, `MainActivity` открывает ссылку в WebView. Без `/.well-known/assetlinks.json` с SHA-256 ключа подписи ссылки (и вход из письма) открываются в браузере.
- Ключи подписи (`*.jks`, `keystore.properties`) — только локально/в менеджере секретов.
- Релиз собирается с R8 (`minifyEnabled true`, `shrinkResources true`, `proguard-android-optimize.txt` в `app/build.gradle`) — проверка Google Play «DEX code optimization»: обфускация, оптимизация и сжатие от 25% каждое (до R8 обфускация была 6%). Свои плагины не держи правилами: `@CapacitorPlugin`/`@PluginMethod` сохраняют правила самого Capacitor, `MainActivity` и сервис RuStore — манифест; в `proguard-rules.pro` только номера строк для стека. Не добавляй широкие `-keep class …** { *; }`, `-dontobfuscate`/`-dontoptimize` и `android.enableR8.fullMode=false` — оценка снова упадёт. Новый нативный код, который находится по имени (рефлексия, `@JavascriptInterface`), — узкое правило на один класс и проверка релизной сборки на устройстве. `mapping.txt` (`app/build/outputs/mapping/release/`) — к каждой версии в Play (App bundle explorer → Downloads), иначе стеки падений нечитаемы. Сборка — JDK 21 (`JAVA_HOME=/opt/homebrew/opt/openjdk@21`): JBR из Android Studio — Java 25, её Gradle 8.14 не читает.
- `/.well-known/assetlinks.json` (`src/app/.well-known/assetlinks.json/route.ts`) подтверждает App Links: SHA-256 релизного ключа (RuStore) зашит, ключ подписи Google Play добавляется в `ANDROID_APP_SHA256` (через запятую). Ответ — 200 без редиректов, иначе Android не подтвердит ссылки.

## Telegram Mini App

- Тот же сайт открывается в Telegram как Mini App; вне Telegram ничего не меняется. `TelegramMiniApp` (корневой layout) включается, только если в hash есть `tgWebAppData` (или маркер в `sessionStorage` после перезагрузки): ставит `data-telegram-app` на `html`, грузит SDK `telegram.org` (разрешён в CSP), ведёт `BackButton` и открывает внешние ссылки через `openLink`/`openTelegramLink`.
- Вход — плагин Better Auth `telegramMiniApp` (`src/lib/telegram-auth.ts`), `POST /api/auth/telegram/sign-in`. Сервер проверяет HMAC `initData` токеном бота и `auth_date` ≤ 24 ч (`telegram-init-data.ts`); клиентским `initDataUnsafe` не доверяй. Связь — строка `account` (`providerId='telegram'`, `issuer='local:telegram'`, `accountId` = Telegram id), уникальность даёт индекс `(issuer, accountId)`; миграция не нужна.
- Новый аккаунт создаётся только явной кнопкой «Продолжить с Telegram» (`createAccount: true`), иначе ответ `unlinked` — чтобы владелец email-аккаунта мог привязать его, а не получить дубль. Почта таких аккаунтов — заглушка `<username>@<id>.telegram.invalid` (`isTelegramPlaceholderEmail`): письма на неё не уходят, отвязать Telegram у такого аккаунта нельзя.
- Панель «Вход и бот Telegram» в настройках (`profile/settings/page.tsx`, стили `.tg-settings-*` в `profile.css`): без привязки — карточка-приглашение по центру (`.tg-settings-invite`), три пункта пользы строками того же островка `.settings-list` и голубая кнопка `TelegramLinkButton` во всю ширину; с привязкой — карточка «Telegram привязан» с чипом «Вход включён», блок бота со своим статусом («Подключён» / «Не подключён» / «Остановлен») и настройками — один островок строк `.settings-list`/`.settings-row` (иконка, название и подсказка `hint` из `TELEGRAM_BOT_OPTIONS`, справа переключатель `.settings-switch`; город — строка с выпадающим списком) и синяя кнопка `.settings-save` (её же берёт панель «Уведомления»: одиннадцать переключателей разложены по четырём островкам с заголовками — `NOTIFICATION_GROUPS` и иконки `NOTIFICATION_ICONS`; новый вид уведомления без группы попадает в последнюю, а иконку требует тип. Переключатель `.settings-switch` — обычный checkbox с `role="switch"`, форма отправляет его как раньше), внизу отдельно — «Отвязать Telegram» с подтверждением (`TelegramUnlinkButton`) или пояснение, что аккаунт, созданный через Telegram, отвязать нельзя.
- Привязка: Настройки → `createTelegramLink` кладёт одноразовый код (хэш в `verification`, 10 мин) и открывает `TELEGRAM_MINI_APP_URL?startapp=link_<code>`; код приходит в подписанном `start_param` и погашается `consumeVerificationValue`.
- Вход на сайте для всех — кнопка «Войти через Telegram» (`telegram-sign-in.tsx`) под полем почты (раздел «Вход и CanRush для бизнеса»). Внутри Mini App кнопка входит по `initData` (поле почты скрыто), в браузере — через бота: `POST /api/auth/telegram/login/start` кладёт в `verification` состояние под `telegram-login:<sha256(token)>` на 5 минут и ставит подписанную cookie с nonce, браузер открывает `t.me/<bot>?start=login_<token>` и опрашивает `/telegram/login/poll`. Бот (`telegram-bot/login.ts`) присылает «Подтвердить вход / Это не я» и меняет состояние; poll проверяет nonce (вход начат в этом браузере), погашает строку один раз и создаёт аккаунт, если Telegram ещё не привязан. Не убирай шаг подтверждения в боте — без него чужая ссылка `login_` впустила бы злоумышленника в аккаунт того, кто нажал Start. Работает только при живом webhook.
- `TELEGRAM_BOT_TOKEN` и `TELEGRAM_MINI_APP_URL` — в `apps/site/.env.local`; без них функция выключена. Telegram Web (web.telegram.org, iframe) не поддерживается: `frame-ancestors 'none'`/`X-Frame-Options: DENY` оставлены намеренно.
- Нижние отступы в Mini App учитывают `--tg-safe-area-inset-bottom` (правило таб бара в `globals.css`). Тесты: `test/telegram-init-data.test.ts`, `test/telegram-auth.integration.test.ts`.

## Telegram-бот

- Тот же бот, что у Mini App. Код — `apps/site/src/lib/telegram-bot/`, webhook — `POST /api/telegram/webhook` (проверяет `X-Telegram-Bot-Api-Secret-Token` = `TELEGRAM_WEBHOOK_SECRET`; без секрета роут отвечает 404). Регистрация webhook, команд и кнопки меню — `npm -w apps/site run telegram:setup`; inline-режим включается вручную через `/setinline` в @BotFather.
- Миграция `0057_telegram_bot.sql`: `telegramChat` (кто нажал /start, город, переключатели, `blockedAt`), `telegramOutbox` (очередь), `telegramJobRun` (захват периода задачи), `telegramPromoSeen` (уже объявленные акции). Аккаунт находится через `account` с `providerId='telegram'`; без привязки бот умеет только поиск и подборку недели.
- Не шли сообщения напрямую из запросов: пиши в очередь через `enqueueTelegram`/SQL `telegram_enqueue` с уникальным `dedupeKey` — функция сама проверяет чат, блокировку и переключатель. Очередь хранит вид + данные, текст рендерит отправитель (`renderOutboxMessage`), поэтому HTML экранируется в одном месте (`format.ts`).
- Уведомления сайта зеркалит триггер `notification_telegram` (после фильтра настроек сайта). Маркет — `notifyMarket` в `market.ts` внутри той же транзакции; поток сообщений одного заказа — не чаще раза в 10 минут.
- Воркер стартует из `src/instrumentation.ts` в процессе сайта (`TELEGRAM_WORKER=off` отключает): раз в секунду до 20 сообщений (лимит Telegram 30/с), строки берутся с арендой на 2 минуты и `skip locked`; 429 — повтор после `retry_after`, 403 — чат помечается заблокированным. Расписание по Москве: 04:00 чистка, 09:00 сводка админам (только с привязанным Telegram и `siteAdmin`), 10:00 акции на избранное, понедельник 11:00 подборка недели, 13:00–16:00 напоминание о крутке, 18:00–20:00 напоминание о серии. Каждая задача сначала вставляет `(job, period)` в `telegramJobRun`, при ошибке удаляет — так несколько инстансов не дублируют рассылку.
- Напоминания, которые возвращают участника (`src/lib/reminders.ts`, задачи `gacha-reminder` и `streak-reminder` в `TELEGRAM_JOBS`, миграция `0156`): один вид уведомления `reminder`, поэтому в Telegram и push он уходит теми же триггерами, а текст и кнопку даёт `describeNotification`. Вечером — участнику с живой серией от `STREAK_REMINDER_MIN_DAYS` (3) дней, у которого последний день — вчера, а сегодня отметки нет (дни — из `drinkStreakDay`, восстановленные считаются), ссылка на `/calendar`. Днём — тому, кто открывал Банкомат (строка `welcome` в `capLedger`), не брал сегодняшнюю бесплатную крутку и не ждёт напоминания о серии, ссылка на `/gacha`. Тому, кто не реагирует, крутка перестаёт напоминать: через `GACHA_REMINDER_DAYS` (7) дней без единой крутки (от последней крутки, платная тоже считается, или от первого захода) наступает тишина до следующей крутки. Считаем по Банкомату, а не по заходам на сайт: кто каждый день читает ленту и не крутит, тоже не отвечает. Серии такая остановка не нужна — проигнорированная сгорает сама, и напоминать становится не о чем. Ключ `reminder:<день по Москве>` и уникальность `("userId", "eventKey")` не дают второго напоминания за сутки: кто днём получил крутку, вечером о серии уже не услышит. Сайт 18+: текст просит отметить банку, если она была, не подталкивает пить, не обещает награду и не пугает потерей серии. Заблокированным и замороженным не уходит, в настройках выключается (`NOTIFICATION_OPTIONS`, группа «Трекер и Банкомат»), а в запасном контейнере задачи не идут вместе с воркером бота (`TELEGRAM_WORKER: "off"`). У окон есть конец: пропущенный из-за перезапуска прогон не догоняется ночью. Каждый прогон удаляет напоминания прошлых дней, иначе у отсутствующего участника они копились бы в колокольчике; ещё не отправленные при этом тоже не уходят. Тест: `test/reminders.integration.test.ts`.
- Исходящие запросы к Bot API идут на `TELEGRAM_API_URL` (по умолчанию `https://api.telegram.org`, читает `getTelegramApiUrl`; его же использует `telegram-setup.mjs`). С российского хостинга Telegram недоступен, а HTTP-прокси с CONNECT режет ТСПУ по SNI, поэтому на зарубежном VPS стоит reverse proxy со своим доменом и TLS, который проксирует на `api.telegram.org`. Только HTTPS: токен бота передаётся в пути запроса. Входящий трафик ТСПУ тоже режет (`getWebhookInfo` показывает `Connection timed out`), поэтому `TELEGRAM_WEBHOOK_URL` задаёт адрес на том же relay, который пересылает запрос на `/api/telegram/webhook` сайта; заголовок `X-Telegram-Bot-Api-Secret-Token` проходит насквозь. Адрес webhook использует только `telegram-setup.mjs`.
- Переключатели бота общие для `/settings` и страницы настроек — `TELEGRAM_BOT_OPTIONS` (`settings.ts`); имена колонок только из этого списка. Тесты: `test/telegram-bot.test.ts`, `test/telegram-bot.integration.test.ts` (fetch замокан, сообщения не уходят).

## Форма отзыва

- На странице напитка форма свёрнута за кнопкой «Написать отзыв» / «Изменить отзыв» (`ReviewFormPanel`, `review-form-panel.tsx`): шкалы, страна и текст появляются после нажатия, сохранение, «Отмена» и удаление сворачивают её обратно (`onSettled` формы). Форма остаётся смонтированной скрытой — карандаш и корзина на своей карточке отзыва говорят с ней событиями `REVIEW_EDIT_EVENT`/`REVIEW_DELETE_EVENT`, и панель сама раскрывается на карандаш. Гостю — прежнее приглашение войти.
- Там же форма пошаговая (`stepped` у `CatalogReviewForm`, только на странице напитка; правка в профиле — прежняя компактная): 1) «Как вам вкус?», 2) «А дизайн банки?», 3) страна, текст, фото и «Опубликовать». Оценка на шаге — `RatingDial` (`rating-dial.tsx`, стили `.rating-dial*` в `catalog.css`): большое число в центре — поле ввода (`role="spinbutton"`, цифрами с клавиатуры, стрелки, Home/End; ширина в `ch` по числу цифр), по бокам вплотную по базовой линии бледные соседние числа (±1, ±2, за краем шкалы ничего) через три точки-кружка; ряд листается свайпом или мышью (`STEP_PX` на балл, как колесо выбора), соседнее число выбирается нажатием; смена сдвигает ряд и увеличивает новое число (Web Animations, выключено в `prefers-reduced-motion`). Маскот и «N из 10 · настроение» — под числом. Любая смена не с клавиатуры сбрасывает недописанный ввод. Сверху — стрелка «назад» и чипы шагов («Вкус 8», «Дизайн 3», «Отзыв»; пройденные — кнопки; при правке сохранённого отзыва все чипы — кнопки с оценками сразу, чтобы поправить текст, не проходя оценки). Оценки уходят в `FormData` из состояния, поэтому скрытые шаги ничего не теряют; ошибка сервера по оценке возвращает на её шаг, сохранение и «Отмена» — на первый.
- Шкалы «Дизайн» и «Вкус» (1–10, `CatalogReviewForm` в `catalog-review-form.tsx`): справа от ползунка — маскот `RatingFace` (`rating-face.tsx`): банка CanRush в стиле наклеек достижений (синий `#006EFF`, толстый чёрный контур, красная полоса крышки, белая «наклеечная» кайма для тёмных тем), не эмодзи. Пять настроений по два балла (`ratingMood`): низкие оценки наклоняют банку и дают каплю пота, у вкуса наверху язык и красные штрихи, у дизайна — глаза-сердечки и чёрные звёздочки (`currentColor`, светлые в тёмной теме). Маскот декоративный (`aria-hidden`), слово настроения уходит в `aria-valuetext`. Смена настроения — короткий «поп» (`rating-face-pop`, выключен в `prefers-reduced-motion`).
- «Страна производства» — необязательное поле с выпадающим списком `CountryInput` (`country-input.tsx`, стили `.country-input*` в `globals.css`, потому что форма отзыва бывает и в профиле без `catalog.css`): при фокусе — частые страны, разделитель, остальные; ввод фильтрует по названию, флаг-эмодзи (`countryFlag`) стоит перед названием, × очищает. Свободный текст не сохраняется: уход с поля с незнакомым названием возвращает выбранную страну. Подсказка под полем («Изготовлено в…») — карточка `.review-hint-card` (та же, что у индикатора текста, тон фирменный, иконка-глобус). Колонка `review.country` (ISO 3166-1 alpha-2, миграция `0111`), список и названия — `src/lib/countries.ts` (сервер принимает только коды оттуда — `validateReviewInput`). В карточке отзыва — плашка с флагом рядом с датой (`review-item-country`).
- Карточка отзыва (`CatalogReviewItem`) рисует рамку аватарки автора (`AvatarFrame`, `ReviewAuthor.frame` из `profileAppearance` в `REVIEW_SELECT`), как рейтинг и лента; стили рамок — в `profile.css`, поэтому страница напитка подключает его (между `shared.css` и `catalog.css`).
- Под текстом отзыва — `ReviewTextMeter` (стили `.review-meter*` в `globals.css`, форма бывает и в профиле), своя карточка с отступом от поля, фон и рамка тонированы цветом уровня (`--meter`): иконка в кружке, заголовок и подсказка, внизу полоска до подробного отзыва (`DETAILED_REVIEW_LENGTH`) с отметкой порога публикации (`MIN_REVIEW_LENGTH`), иконка и заголовок по уровню из `reviewTextGuidance` — «Ещё N символов до публикации» (серый), «Можно публиковать · а пара деталей сделает отзыв лучше» (синий), с `GOOD_REVIEW_LENGTH` (90) — «Хороший отзыв · ещё N до подробного» (сине-зелёный, вторая засечка на полосе), «Подробный отзыв» (зелёный); иконка коротко «подпрыгивает» на каждом новом уровне. Не красный: короткий текст при наборе — не ошибка. Диктору уходит только смена уровня (`status`), не каждый символ.
- React сбрасывает форму после server action: управляемые `select` и радиокнопки в DOM возвращаются к первому значению, хотя состояние прежнее. Поэтому форма отзыва кладёт оценки и страну в `FormData` из состояния (так же сделаны сахар и сок в заявке напитка). Тесты: `test/rating-face.test.tsx`, `test/review-fields.test.ts`, `test/review-photos.integration.test.ts`.

## Новости (статьи участников)

- `/news` — опубликованные статьи (обложка, заголовок, лид, автор, минуты чтения) и у вошедшего «Мои черновики и заявки»

- Пишет любой участник, публикует команда: `draft` → `pending` (`submitArticle`: заголовок и `ARTICLE_MIN_TEXT` символов,

  Кнопка в редакторе — «Опубликовать»; после неё на странице статьи тост «опубликуем после модерации»
  (`ArticleSentToast`, `?sent=1` убирается из адреса, чтобы перезагрузка не повторяла тост).
- Лайки и жалобы (миграция `0114_article_reactions.sql`): `articleLike` (один на участника, свою статью нельзя —
  `setArticleLike`, `ArticleLikeButton`) и вид жалобы `article` (`CONTENT_REPORT_KINDS`, `CONTENT_SOURCES` — только
  опубликованная). У опубликованной статьи рядом с автором — сердце и меню «⋯» (`MoreActions`: «Пожаловаться», команде —
  «Удалить», `STAFF_DELETE.article`). Свой черновик или отклонённую статью удаляют в «Моих черновиках»
  (`ArticleDraftDelete`) и кнопкой-корзиной в редакторе (`deleteDraftAction`).
- Канал автора (миграция `0115_article_channel.sql`, колонка `article.telegramChannel`): под текстом в редакторе —
  «Прикрепить Telegram-канал» (поле `t.me/…`) и кнопка «свой @канал» из профиля (`profileChannel`); неготовое имя
  не отправляется, остальное сохраняется. Правила — `parseArticleChannel`. Под статьёй — строка «Канал автора @…»

- Галерея: подряд идущие блоки «Фото» складываются в сетку `.article-gallery` (2 колонки, у трёх первое — во всю
  ширину), одиночное фото — во всю ширину. Обложка и каждое фото — кнопка с `data-photo`: `ArticleGallery`
  (`article-gallery.tsx`, клиентская обёртка над серверным текстом) открывает тот же `PhotoViewer`, что у отзывов,
  со всеми фото статьи по порядку (`articlePhotos`: обложка, затем блоки) — листание, свайп и зум.
- Карточка в «Новостях»: справа от автора — иконка Telegram-канала статьи (если прикреплён) и `ArticleLikeButton`
  (лайк прямо из списка; `listPublishedArticles` отдаёт `liked` для зрителя, у своей статьи — только число).
- SEO: `generateMetadata` даёт canonical `/news/<id>`, Open Graph `article` (даты, автор, обложка как картинка) и
  `twitter: summary_large_image`; опубликованная статья несёт JSON-LD `Article` (заголовок, описание, даты, автор,
  издатель, обложка). Адрес — id без человекочитаемого слага.
- Править можно только черновик и отклонённую. На проверке или опубликованную автор сначала возвращает в черновики
  (`reopenArticle`; опубликованная скрывается до повторной проверки). Удаляет автор или команда (`adminAuditLog`, `article`).
- Миграция `0113_articles.sql`: `article` (блоки — jsonb) и `articleImage` (обложка и фото блоков, удаляются со статьёй).
  Фото видны всем, только пока статья опубликована: `/api/article-images/[id]` (`?thumb` — для карточек, `ARTICLE_MEDIA`).
  Опубликованные статьи — в sitemap.
- Редактор `ArticleEditor` (`article-editor.tsx`, стили `news.css`) — как Notion, без сторонних библиотек: каждый
  текстовый блок — свой contenteditable, React хранит только список блоков; DOM блока заполняется один раз при
  монтировании и читается обратно на `input`.
  - Enter делит блок по курсору (список продолжается, пустой пункт заканчивает список), Backspace в начале снимает тип
    или склеивает с предыдущим, стрелки переходят между блоками.
  - «/» — меню блоков с фильтром. Markdown в начале строки: «# », «## », «### », «- », «1. », «[] », «> », «!! », «---».
    После снятия префикса курсор остаётся на своём месте: клавиатуры телефонов отдают слово целиком.
  - Выделение — плавающая панель (жирный, курсив, зачёркнутый, код, ссылка; Cmd/Ctrl+K; цвет — «Вторичный», «Синий»,
    «Красный» или «Обычный», `TEXT_COLORS`). Цвет ставит `execCommand('foreColor')` (тег `<font color>`), а хранится
    `<span data-color>`, который страница красит по теме; «Обычный» пишет цвет вне палитры, и санитайзер его снимает.
    Вставка — простым текстом, строки — отдельными абзацами.
  - Футер лежит над поверхностью страницы (`z-index` 2 против 1), поэтому пока открыто меню блоков или панель,
    `.main-surface:has(.ae-menu, .ae-format)` поднимается над ним — иначе меню у низа страницы обрезалось.
  - Слева от блока на компьютере «+» и ручка «⋮⋮» (перетаскивание и меню: превратить в, дублировать, выше/ниже,
    удалить); на телефоне вместо них панель над таб баром.
  - Блоки: текст, H1–H3, списки, чек-лист, цитата, выноска, разделитель, фото, напиток из каталога (`StoreDrinkPicker`).
  - Автосохранение через 1,2 с после правки (`saveArticleAction`, сверка версии против второй вкладки). Первое
    сохранение создаёт черновик и меняет только query (`?id=`): смена пути заставила бы роутер Next смонтировать
    страницу правки и потерять набранное. Id первого блока пустой статьи постоянный — случайный ломал гидрацию.
- Правила документа — `article-fields.ts` (общие для браузера и сервера): известные типы, лимиты и белый список
  инлайн-разметки `sanitizeInline` (b, i, s, code, a с http(s) или путём сайта, span цвета из палитры, br; div Chrome
  → перенос строки). Для отправки нужен заголовок и `ARTICLE_MIN_TEXT` (50) символов текста.
  Разметка пересобирается тег за тегом при сохранении и ещё раз при выводе. Сервер выкидывает фото не этой статьи и
  напитки не из каталога (`cleanBlocks`). Тесты: `test/article-fields.test.ts`, `test/articles.integration.test.ts`.

## Лента

- `/feed` — все стены одной лентой: те же записи `profileComment`, без отдельной таблицы и копий. Запись из ленты пишется на стену автора (`profileId = userId`), запись на любой стене сразу видна в ленте; удаление, реакции и комментарии общие. Не заводи для ленты отдельное хранилище — связь держится на том, что это одна строка.
- Запрос — `getFeed` в `profile-community.ts` (колонки общие со стеной, `WALL_POST_COLUMNS`); вкладка «Подписки» — свои записи и записи авторов/стен, на которые подписан зритель. Карточка записи — `WallPost` (`wall-post.tsx`) и на стене, и в ленте; в ленте показывает «на стене …», если запись на чужой стене.
- Правка: записи стены и комментарии (отзывы, тирлисты, стена) редактирует только автор; владелец стены может лишь удалить чужую запись. `editedAt` (миграция `0053`) показывает метку «изменено». Иконки действий — `action-icons.tsx`. Лайки комментариев стены — `wallReplyLike` (`0052`), свой комментарий лайкнуть нельзя.
- Ответы в обсуждениях (отзывы, тирлисты, стена): `replyToId` + `replyToUserId` (миграция `0055`). Адресата сервер берёт из комментария того же обсуждения, а не от клиента; ник адресата хранится отдельно и остаётся после удаления исходного комментария. Триггер `notify_comment_reply` шлёт уведомление `comment-reply`, кроме ответа самому себе и ответа автору отзыва (тот уже получает `review-comment`).
- Вложения в комментариях (отзывы, тирлисты, стена) — по правилам записей стены: до 5 фото/GIF и одно видео, та же `prepareWallMedia`. Таблица `commentMedia` (миграция `0077`) с тремя FK на таблицы комментариев (ровно один заполнен, удаляются вместе с комментарием), отдаётся через `/api/comment-media/[id]` — общий `serveStoredMedia` с `/api/wall-photos` (Range для видео). С вложениями комментарий уходит в server action как FormData (`text`, `replyToId`, `photos`, `videoPoster`), без них — как раньше. Выбор, проверка и превью вложений — общий `useMediaAttachments` (`media-attachments.tsx`) у стены и комментариев. Комментарий или запись могут быть только вложением без текста (миграция `0078`: CHECK текста — лишь до 1000 символов, а «текст или вложение» проверяет отложенный constraint-триггер `require_text_or_media` при коммите, потому что вложения вставляются после строки). Правка текста по-прежнему требует текст.
- Вставка из буфера обмена (`pastedFiles`, `src/lib/clipboard-files.ts`): в полях стены и комментариев вставленные картинки и видео становятся вложениями, в форме отзыва — фото отзыва, `MarketPhotoPicker` (объявления, магазины, чат) ловит вставку картинки на всей странице. Обычный текст вставляется как обычно.
- Упоминания `@ник` в комментариях (отзывы, тирлисты, стена) и записях стены/ленты: `MentionText` подсвечивает их ссылкой на профиль, `MentionTextarea` подсказывает ники при вводе (`/api/mentions`, только для вошедших, по префиксу). Правило «@ не внутри слова, почты или ссылки» общее для сайта (`src/lib/mentions.ts`) и БД: триггер `notify_mentions` (миграция `0076`) шлёт уведомление `mention` (не автору, не адресату ответа, не владельцу отзыва/стены — они получают своё), ключ `mention:<таблица>:<id>:<user>`, поэтому правка уведомляет только новых упомянутых. Меняя правило, меняй его в обоих местах.
- Вложения стены (`wallPhoto`, миграция `0056`): `kind` image/gif/video. Тип определяется по содержимому (`prepareWallMedia` в `wall-media.ts`), а не по MIME браузера: GIF перекодируется в анимированный WebP, видео — только MP4/WebM (QuickTime отклоняется), одно на запись, до 20 МБ, с превью-кадром, снятым в браузере и перекодированным сервером. `/api/wall-photos/[id]` отдаёт видео по Range (Safari без этого не играет), `data` хранится с `storage external`, чтобы `substring` читал только нужный кусок. Лимит тела запроса — 26 МБ и в Next, и в `Caddyfile`; меняй их вместе.
- Повышение ранга в ленте: таблица `rankUp` (миграции `0079_rank_up_feed.sql`, `0080_rank_degrees.sql`), одна строка на участника, ранг и степень: Золото и Платина объявляются один раз (степень 1), Легенда — каждая степень. Её пишет триггер `rank_up` на вставку в `profileExperience` — через неё проходят все начисления XP; при прыжке через несколько рангов объявляется только старший. SQL `experience_level()` и `rank_up_step()` повторяют `experienceLevel` и `LEVEL_TIERS`: меняя формулу, пороги рангов или `LEGEND_DEGREE_STEP`, меняй и их (сверяет `test/rank-up.integration.test.ts`). `getFeed` сливает записи и события одним `union all` и отдаёт `items`; карточка — `RankUpCard` (`rank-up-card.tsx`, стили в `feed.css`, эффект нарастает от Золота к Легенде, тёмные темы сайта учтены). Заблокированные и участники без ника в ленту не попадают.
- События в ленте, кроме ранга: опубликованный тирлист (`kind: 'tierlist'`, по `publishedAt`, карточка — та же `TierListCard` с лайками) и оценки напитков (`kind: 'reviews'`): все отзывы одного участника за московский день — одно событие с ключом `<userId>|<YYYY-MM-DD>` (`getReviewsByAuthorDays` в `reviews.ts`), чтобы серия отзывов не забивала ленту; в карточке видна одна оценка в стиле сайта (фото банки на всю высоту, бренд серым чипом, оценка синей «таблеткой» со звездой, дизайн/вкус, три строки текста), ссылка на отзыв; остальные отзывы того дня (они уже загружены с карточкой) лежат «стопкой» — под карточкой выглядывают края одной-двух следующих (`.feed-reviews-stack`); стопка или кнопка «Посмотреть больше · ещё N» раскрывает их на месте, «Свернуть» собирает обратно (`FeedReviewsMore`, `feed-reviews-more.tsx`, `REVIEWS_SHOWN` = 1), лайки подгружаются для всех; у каждого напитка сердце в правом верхнем углу — лайк отзыва прямо из ленты (`TierLikeButton kind="review"` → `reviewDiscussionAction(id, 'vote')`, свой отзыв — только счётчик). - `siteAdmin.role` (миграция `0103`): `admin` и `moderator`, владелец — всегда `admin` (check `siteAdmin_owner_is_admin`). Тип и подписи — `src/lib/admin-roles.ts` (без БД, его импортируют компоненты).
- Модератор: аналитика, заявки магазинов и напитков, жалобы, удаление контента (тирлисты, отзывы, комментарии, стена, объявления), блокировка участников (админов и модераторов заблокировать нельзя). Почту участников он не видит: `getAdminDashboardData(..., showEmails=false)` подставляет `@ник` и не ищет по email. Ему закрыты «Администраторы», «Кампании», «Конкурс» и передача магазина — `requireFullAdmin` (редирект на `/admin?error=forbidden`), в сайдбаре они скрыты (`ADMIN_ONLY_SECTIONS` в `admin-shell.tsx`).

SQL-проверки модерации магазинов и напитков (`exists siteAdmin`) пускают обе роли; тег `admin`, сводка бота и флаг админа в боте — только `role = 'admin'`.

В строках авторов тег роли показывается, только пока роль совпадает: `role = u."profileTags"[1]` во всех запросах с тегом. Список достижений показывает его админам и самому модератору. - Удаление на месте: у чужих отзывов, комментариев (отзывы, тирлисты, стена), записей стены и ленты, тирлистов и историй админ и модератор видят «Удалить» в меню «⋯» (`StaffDeleteMenuItem`, рядом с «Пожаловаться») — без захода в админку. ## Ошибки сайта

- Свой сбор без сторонних сервисов: с российского хостинга они ненадёжны и уводят данные наружу. Таблица `errorGroup` (миграция `0157`) — одна строка на группу: источник (`server`/`client`), последний путь, сообщение, начало стека, `count`, первое и последнее время, `notifiedAt`, `hiddenAt`. Логика — `src/lib/error-log.ts`, чистка и группировка без БД — `error-log-fields.ts`.
- Сервер: `onRequestError` в `src/instrumentation.ts` → `recordServerError`, только production (`ERROR_LOG=off` выключает, в разработке — `ERROR_LOG=on`); страницы, роуты и server actions. `redirect()`, `notFound()` и обрывы соединения не считаются (`isIgnoredError`). Ошибки фоновых воркеров сюда не попадают: они вне запроса, их видно в логах контейнера. Сбой записи только пишется в лог и не мешает ответу.
- Браузер: `global-error.tsx` (свой документ вместо корневого layout: логотип, «Обновить» — полная перезагрузка, «На главную»; стили — `globals.css` и `site-theme.css`, тема — из cookie, шрифт — `src/app/fonts.ts`; inline-`<style>` запрещён CSP) и `error.tsx` разделов зовут `useErrorReport` (`client-error-report.ts`), новый `error.tsx` — тоже. Хук шлёт beacon на `POST /api/client-errors`: свой origin, не боты, 10 в минуту с IP, до `CLIENT_REPORT_LIMIT`. Ошибка с `digest` пришла с сервера и уже записана — браузер её не шлёт. Ошибки вне рендера (обработчики событий, `unhandledrejection`) не собираем.
- Без персональных данных: `cleanError*` оставляют путь без query и хэша (`/profile/[ник]`, id и длинные ключи скрыты), сообщение без почты, токенов, данных URL и чисел, из стека — только кадры (строка и колонка остаются). Cookie, заголовки, тело запроса и IP не сохраняются. Новое поле отчёта проводи через эту же чистку; всё из браузера — чужой текст.
- Группа — хэш источника, места и очищенного сообщения: на сервере место — `context.routePath` (`/catalog/[slug]`), в браузере маршрута нет — первый сегмент пути. Числа и id вырезаны, поэтому одна ошибка на разных строках — одна группа. Стек в хэш не входит: минифицированные имена меняются с каждой выкаткой, и скрытая ошибка всплывала бы снова.
- Оповещение: группа пишет админам (`telegramAdminIds`, как у сводки: `siteAdmin.role = 'admin'` с привязанным Telegram) в очередь `enqueueTelegram`, вид `error-alert` — при первом появлении и при повторе, если с прошлого сообщения прошёл час (`notifiedAt` под блокировкой строки, `dedupeKey` = `error:<хэш>:<час>:<админ>`). Отметка и сообщения — в одной транзакции. Своего переключателя в боте нет, шумную группу убирает «Скрыть». Предохранители, потому что адрес приёма открыт всем: `ALERTS_PER_HOUR` на источник — браузер не тратит лимит сервера, группа сверх лимита напишет при следующем повторе; `MAX_CLIENT_GROUPS` — новые группы браузера сверх него не создаются, повторы и сервер считаются.
- Просмотр — `/admin/errors` (группа «Система», только `requireFullAdmin`, в `ADMIN_ONLY_SECTIONS`): «Активные / Скрытые», повторы, последнее время, стек под `details`, «Скрыть» / «Вернуть» (журнал `adminAuditLog`: `error-hide`, `error-show`). Скрытая группа считается дальше, но не пишет. Группы, молчащие 30 дней, удаляет утренняя чистка `pruneErrorGroups` (задача `prune` воркера Telegram). Тесты: `test/error-log-fields.test.ts`, `test/error-log.integration.test.ts`, `test/client-errors-route.test.ts`, `test/instrumentation.test.ts`.

## Разметка для поисковиков

- Страница напитка выводит Schema.org `Product` (`drinkJsonLd` в `src/lib/drink-json-ld.ts`): название (полное, если есть), бренд, обложка, описание бренда, `AggregateRating` — средняя оценка участников из 10 с числом отзывов — и `AggregateOffer` — цены города от и до в рублях с числом предложений. Без отзывов и без цен разметки нет: поисковики считают такой Product ошибкой. Статьи — `Article` (раздел «Новости»). Тест: `test/drink-json-ld.test.ts`.
- Превью ссылок (Telegram в первую очередь): `og:image` 1200×630 и `twitter:card summary_large_image` у всех страниц. Next заменяет объект `openGraph` целиком на каждой странице, поэтому `seoMetadata` сам подставляет `DEFAULT_OG_IMAGE`, а своя картинка передаётся как `image: ogImage(путь, alt)`; страница со своим `openGraph` мимо `seoMetadata` (статьи, компании) называет `images` сама, иначе останется без картинки. Закрытые страницы наследуют общую картинку из корневого layout — своих картинок им не делай.
- Картинки рисуют обработчики `src/app/og/*`, разметка — `src/lib/og-image.tsx`: `/og/default` (общая), `/og/drink/<адрес>` (обложка, бренд, вкус, средняя оценка), `/og/tierlist/<адрес>` (название и автор; у черновика и несуществующего — общая картинка, час кеша вместо суток: удалённый список не должен долго светить названием), `/og/gacha/<ключ сезона>` (постер `scene.poster` на месте плитки; пока идёт сезон, адрес даёт `generateMetadata` страницы — константа `metadata` застряла бы на сезоне запуска сервера). Постер 720×700, поэтому напрямую в `og:image` его не ставим. Файловая конвенция `opengraph-image` в standalone работает, но на `/catalog/*` и `/tierlists*` `proxy.ts` ставит `no-store`, поэтому адреса вынесены в `/og`; в `/api/` нельзя — закрыт в `robots.txt`. Ответ — JPEG (PNG с фото банки тяжелее 300 КБ), `Cache-Control: public`, готовая картинка ещё и в памяти процесса (`ogResponse`, до 300 штук): рисование занимает главный поток. Обложки — только свои (`coverBytes`: файлы `public/` и фото из базы), чужой адрес заменяется артом каталога. `next/og` не читает woff2, поэтому рядом лежат OTF (`fonts/*.otf`, в standalone их кладёт `outputFileTracingIncludes`). Глиф, которого нет в шрифте, и эмодзи `next/og` идёт скачивать в Google Fonts и на CDN прямо при рисовании, поэтому весь текст картинок проходит через `ogText`; шрифт сменился — обнови там список символов. Тест: `test/og-image.test.tsx`.

## Коллекция вкусов

- Своей таблицы нет: вкус считается попробованным, если у пользователя есть отзыв (`review`) или банка из каталога в `drinkLog`. Набор вкусов — `storeDrinkOptions` без «в ассортименте», бренды меньше чем с `MIN_COLLECTION_SIZE` вкусами не показываются, а попробованные вкусы, которых больше нет в каталоге, не считаются. Старые идентичности из отзывов приводятся через `canonicalDrink`.
- Линии со своим брендом в каталоге собираются вместе с основным брендом: `COLLECTION_BRAND_LINES` (Adrenaline Game Fuel → Adrenaline Rush, название с префиксом линии).
- Опыт: вехи 25/50/75/100% бренда (`COLLECTION_MILESTONES`), `reason='collection'`, `sourceKey` = `<бренд>:<процент>` — ключ по доле, а не по числу вкусов, поэтому рост каталога не платит повторно. У маленьких брендов доли, достигаемые одним и тем же числом вкусов, сливаются в старшую (`brandMilestones`). Подсказка «Ещё N до X%» берёт уже выплаченные доли из журнала опыта (`BrandCollection.paid`, `paidShares`): если каталог вырос после 100% (3/3 → 3/4), 100% не обещаются повторно, 75% доплачиваются, а заголовок пишет «бонусы уже получены». Начисляет `getBrandCollections` — при просмотре коллекции/профиля, после отзыва и после банки из каталога в календаре.
- Дубликаты вкусов в коллекции — почти всегда архивные идентичности из `product-registry.json` без предложений: у них то же фото, что у живого товара. Их склеивают алиасами в `REVIEWED_PRODUCT_ALIASES` + миграцией данных (`0060_archived_duplicate_aliases.sql`, переносит и `drinkLog`). Burn `peach` тоже такой дубль: на обложке архивной карточки банка «Персик Манго Zero Sugar», он склеен с `blend:mango+peach:sugarfree` (`0070`); обычного Burn с персиком нет. По жалобам участников так же склеены (`0075`): Lit Energy «Ягодный» → Classic (`original`), Flash Up «Барбарис» → Ultra, Pulseup «Вкус не уточнён» → Your Energy и «Pulse Up» Ягодный → Pulseup. Бренд «Pulse Up» парсер теперь сам приводит к Pulseup (бренд в `config/products.json`). Так же (`0082`): Flash Up «Манго» (старый дизайн) → манго-ананас, Ninja «Персик»/«Вишня» → Ninja Star (Едадил давал бренд «Ninja»; сам Ninja — это только «THE NINJA» Cheerio 250 мл), а «Adrenaline Game Fuel» Манго → Adrenaline Rush `mango`: манго перешёл из Game Fuel в Vitamin Power, в магазинах продаётся под обоими названиями (фото в магазинах — чёрная банка Vitamin Power). Старая синяя банка Game Fuel «Mango Storm» (снята с производства) — другой напиток: `Adrenaline Rush` + `game_fuel_mango` («Game Fuel · Mango Storm»); в заявке и в правке админки это свой вкус «Mango Storm» (или «Game Fuel Манго») — алиасы ведут его туда, а не в манго Vitamin Power. Так же (`0096`): HQD Energy — это Ashkudi (в 2025 переименован, те же банки и обложки; парсер читает «HQD»/«Эйч Кью Ди» как Ashkudi), а «Мандариновый пуэр» — банка By Баста («by БАСТА ГУФ»), не Doma By Guf: парсер знает бренд By Баста, и более длинное «Баста» побеждает «Гуф» в названии. Напиток участника склеивают так же (`0101`): Piranha's «berry» («slam classic energy») — та же банка, что `original` парсера, поэтому `move_drink_identity` перенёс данные, дубль из `catalogDrink` удалён, а хэш-адрес — в реестре; так же (`0102`) «100 Kwt atomic citrus» → «100 Kwt · Грейпфрут + Апельсин» (по просьбе владельца, хотя банка — серебряная коллаборация Atomic Heart) и «X-Turbo персик сакура» → «X-Turbo · peach» (старый дизайн Персик-Сакура). ## Конкурсы

- Реестр — `CONTESTS` в `src/lib/contest.ts`: ключ (пишется в `contestDraw.contest` и в URL админки), приз, тексты баннера, картинка, дни приёма (`firstDay`/`lastDay` по Москве, банка в календаре выпитого в эти дни — участие), день итогов и секретный тег победителя. Новый конкурс — новая запись; ключ потом не меняй. Фазы `upcoming` → `open` → `results` → `over`; `currentContest` выбирает самый ранний идущий: на главной он — иконка «Конкурс» в ряду `HomeServices`, а `ContestBanner` — шапка `/contest` (правила). Розыгрыш доступен только после конца приёма, `crypto.randomInt` по пулу; в `contestDraw` (миграция `0072`) сохраняются победитель, id пула и фильтры, всё пишется в `adminAuditLog`. Открытый победитель у конкурса один (частичный уникальный индекс + advisory lock).

## Топ месяца

- Гонка — XP, набранный за календарный месяц по Москве (без самих наградных XP). Итоги подводит идемпотентная `settle_monthly_top()` (миграция `0050_monthly_top.sql`), её вызывают главная и `/leaderboard` через `settleMonthlyTop()`; первый подсчёт — за октябрь 2026. Топ-3 получают +1000/+600/+300 XP (миграция `0107`, до неё было +500/+300/+150; выплаченное не пересчитывается; `MONTHLY_TOP_REWARDS` в `monthly-top.ts` и `settle_monthly_top` меняй вместе) (`reason='monthly-top'`), достижение и тег `top` («ТОП», легендарный) и уведомление `monthly-top`.
- Блок «Топ-3 за месяц» на `/leaderboard` (`MonthlyTop`, стили в `leaderboard.css`) рисует лидеров теми же строками `lb-*`, что и рейтинг за всё время: место с медалью, аватар с рамкой, ник и тег, XP за месяц и справа награда за место (у первого — золотая); первое место — та же мягкая подсветка.

- Ряд кружков в самом верху главной (`HomeStories` → клиентский `StoriesStrip` в `stories-strip.tsx`, стили `src/styles/stories.css`, их импортирует только главная). Текста минимум — не возвращай списки и абзацы. Ключ `telegram:v2` — новая кампания меняет версию, и кольцо снова загорается; затем истории участников (непросмотренные и подписки раньше).
- Истории участников: таблица `story` (миграция `0090_stories.sql`) — одно фото, GIF или видео по правилам вложений стены (`prepareWallMedia`) и подпись до 200 символов; живут `STORY_HOURS` (24 ч, фильтр в запросах), строки старше недели удаляются при следующей публикации, до `MAX_STORIES_PER_DAY` за сутки, нужен ник, заблокированные не публикуют и не показываются (`src/lib/stories.ts`, константы — `story-limits.ts`, клиенту можно импортировать только их). Медиа — `/api/story-media/[id]` (`serveStoredMedia`, Range для видео) только пока история активна. Просмотры — `storyView`, гасят кольцо. Лайки — `storyLike` (миграция `0093_story_likes.sql`, `setStoryLike`/`likeStoryAction`): сердце внизу справа рядом с подписью, одно на человека, своё нельзя, при блокировке в любую сторону и у заблокированных — нет; автор вместо сердца видит лайки и просмотры, по нажатию — список лайкнувших (`getStoryLikers`, только автору). Уведомлений о лайках историй пока нет. Автор удаляет свою историю в «⋯», остальные жалуются (`CONTENT_REPORT_KINDS.story`). Заблокированный участником автор ему не показывается (`notBlockedBy`).
- «Твоя неделя» (`getWeeklyDigest` в `story-digest.ts`) и «Тебе понравится» (`getRecommendations`) не хранятся, а собираются на лету для вошедшего. «Твоя неделя» приходит раз в неделю: с понедельника — итоги прошедшей недели (пн–вс по Москве, `getWeeklyDigest(…, прошлое воскресенье)`), ключ `week:<понедельник>`; просмотренная, она, как NRJ PARTY, уходит из ряда до следующего понедельника (`shown`). «Тебе понравится» обновляется каждый день (`picks:<день>`). Неделя — 7 дней по Москве, заканчивающиеся днём `to`: банки (и по дням, `daily`), серия, XP, отзывы, новые вкусы, место в рейтинге, вкус недели и `ahead` — какой доле отмечавших на этой неделе ты обошёл по банкам. Подача — как Spotify Wrapped (`DigestPage`: вступление, банки со столбиками дней, вкус недели с обложкой, прогресс, открытия, итоговая карточка; классы `.wrap*` в `stories.css`: свой цвет на слайд, плывущие фигуры, строки въезжают по `--line`); на светлых слайдах `data-tone=light` делает шапку тёмной. Пустая неделя — один слайд «Тихая неделя». Рекомендации — гибридная модель `rankRecommendations` (`story-recommendations.ts`, чистая): мнения каждого участника в [-1, 1] (оценка вкуса наполовину абсолютная, наполовину относительно его собственной средней; избранное ≥ 0,8; банки календаря — 3+ раза 0,7, 2 раза 0,5, одна — «пробовал» 0,2); похожесть — косинус мнений по общим напиткам с затуханием при малом пересечении плюс общие любимые бренды, соседи — выше 0,15, не больше 25; предсказание соседей с доверием по числу мнений (70%) + собственная тяга к бренду, семействам вкусов (`tasteTokens` из `profile-compatibility.ts`) и zero sugar (30%), +0,05 за наличие в магазинах, не больше двух напитков бренда; у каждого пункта объяснение (`similar`/`brand`/`flavor`). Кандидаты — до 60 участников с ≥2 общими напитками (избранное, отзывы, календарь), только неиспробованное и только из каталога города; меньше трёх — «Популярно у сообщества». Просмотр системных историй помнит браузер (`localStorage`). Тесты: `test/story-recommendations.test.ts`, `test/stories.integration.test.ts`.
- «Поделиться» в шапке просмотрщика: «Твоя неделя» уходит картинкой 1080×1920 (`renderWeekShare` в `week-share-image.ts`, canvas в цветах слайдов) — в приложении через `nativeImage().share`, в браузере телефона через `navigator.share` с файлом, на компьютере скачивается PNG; рекомендация — ссылкой на напиток; история участника — ссылкой `/?story=<id>`: главная передаёт её в `HomeStories openStory`, и просмотрщик открывается сразу на этой истории, пока она жива.

## Банкомат (гача)

- Альбом красится темой профиля, как трекер и коллекция: страница в списке `.main-surface:has(…)` в `globals.css` (иначе тема закрашивает только колонку), цвета — только `--color-*`, панель карточки — `--profile-panel`. `--color-brand` внутри темы — её акцент (у тёмной почти белый), поэтому синяя кнопка и `--rarity` редкой берут `#006eff` напрямую.
- Вид редкости — как у рангов, общий для результата крутки, альбома, ленты и блока профиля: `rarity-badge.tsx` (`RarityChip` — металлическая таблетка с фигурой, `RarityEmblem` — эмблема с молнией, `RarityShine` — первый ребёнок `.rarity-card`), стили и токены `--rarity-light/mid/dark/ink/glow` по `data-rarity` — в `shared.css`, фигуры — `LEVEL_SHAPES` из `level-badge.tsx`. Эффекты растут с редкостью: у обычной нет, редкая — блик, эпическая — ещё искры, легендарная — быстрый блик по рамке и пульс свечения; всё выключено в `prefers-reduced-motion`. Для слабых телефонов анимируются только `transform` и `opacity` (не `background-position`, не тень), альбом и карточки ленты держат `content-visibility: auto` с полями под свечение, а в альбоме блик есть только у эпических и легендарных, без искр и пульса: на 276 карточках было 227 анимаций (9 с перерисовкой каждый кадр), стало 44 на всю страницу и 12 в первом экране, все только на видеокарте. Обложка лежит над бликом (`z-index: 1`), значки — над обложкой.
- `/gacha` — автомат с карточками банок из каталога, альбом — `/profile/<ник>/cards`; иконка «Банкомат» в ряду `HomeServices` (`public/brand/home/gacha.svg`, SVG в стиле наклеек — `unoptimized`). Правила без БД — `src/lib/gacha-fields.ts` (редкости, шансы `RARITY_ODDS` в промилле, гарант, цены, `CAP_SOURCES`), сервер — `src/lib/gacha.ts`, автомат — `GachaMachine` (`gacha-machine.tsx`, server action `pullAction`), стили — `src/styles/gacha.css` (страницы подключают ещё `shared.css` и `profile.css` ради `.settings-list`).
- Валюта — «крышки», только заработанные: журнал `capLedger` (миграция `0154`, ключ источника уникален, баланс — сумма), начисляют триггеры через `award_caps` (блокированным не платит, `daily` — лимит за московские сутки): банка в трекере +3 за день, отзыв +10 (3 в сутки), опубликованный тирлист +15 (1 в сутки), 10 свайпов за сутки +2, вехи серии трекера (`drink-streak` в `profileExperience`) 7/14 — +20, от 30 — +60; первый заход в автомат — +`WELCOME_CAPS` (`welcome`). Меняя суммы, меняй триггеры и `CAP_SOURCES` вместе. Триггер серии платит только в момент достижения вехи, поэтому тем, кто прошёл 7 или 14 дней до запуска Банкомата, миграция `0163` разово доплатила по живым сериям теми же суммами и ключами `<первый день>:<веха>`: двойной выплаты нет, следующие вехи платит триггер, а уведомления о доплате нет. Купить крышки нельзя ни прямо, ни через тариф — иначе это лутбокс за деньги (требования магазинов и закона), у крышек и карточек нет денежной ценности и обмена.
- Крутка (`pullGacha`): одна транзакция под блокировкой участника — бесплатная раз в московские сутки (`gachaPull.freeDay`, уникальный индекс), иначе 10 крышек, ×10 — 90; сначала редкость (`rollRarity`, `crypto.randomInt`), потом банка внутри неё (`pickFromPool`, пустая редкость отдаёт ближайшую). Гарант по журналу `gachaPull`: эпическая и выше — не реже раза в `PITY_EPIC` (10), легендарная — в `PITY_LEGENDARY` (60). Клиент только показывает результат.
- Пул (`gachaPool`, кеш 10 минут на процесс): весь каталог (`loadAllCatalogGroups`) с локальной обложкой и `isCountedCatalogDrink`. Редкость — из данных (`rarityOf`): 3+ сети с действующими ценами во всех городах — обычная, 1–2 — редкая, без магазинов — эпическая (архив), напиток участника без магазинов, снятый с производства или из `LEGENDARY_DRINKS` — легендарная. Редкость фиксируется в `gachaCard`/`gachaPull` в момент крутки и не падает, если напиток появится в магазинах. Склейка напитков (`move_drink_identity`) переносит карточки и крутки, складывая счётчики.
- Осколки (миграция `0155`, журнал `shardLedger`, отдельный от крышек): дубль приносит `DUPE_SHARDS` (1/3/10/30 по редкости, ключ — крутка), крафт недостающей карточки стоит `CRAFT_COST` (20/60/200/600 по редкости банки в пуле сейчас, ключ — напиток, `craftCard`, `gachaCard.crafted`). ## Экран загрузки

- Файлов `loading.tsx` и скелетонов нет намеренно: при переходе текущая страница остаётся на экране, а `NavigationProgressProvider` показывает `SiteLoading` (пиксельные буквы Canrush, CSS keyframes, без JavaScript) поверх, только если переход дольше `NAVIGATION_LOADING_DELAY_MS` (800 мс). Скелетоны пробовали и откатили: мигали на быстрых переходах, прятали фон темы профиля и зацикливали некоторые страницы профиля. Не возвращай их без отдельного решения.
- Геометрия и длительность цикла находятся в `src/lib/loading-word.ts`. Уважать `prefers-reduced-motion`. Анимация должна работать в потоковом fallback до гидратации страницы.

## Mobile First

- Сайт и Android-приложение открывают в основном с телефона: каждую страницу, форму, диалог и кнопку сначала делай под экран 375 px, потом расширяй до компьютера. Проверяй в эмуляции телефона (375×812, светлая и тёмная тема), а не только на широком экране.
- Кнопки на телефоне (до 639 px) — во всю ширину своего блока: одиночная кнопка действия («Показать ещё», «Добавить напиток», «Сохранить») растягивается до краёв (`width: 100%`, текст по центру), несколько кнопок встают друг под другом, главная сверху. Узкая кнопка посередине (`width: fit-content`) допустима только с 640 px. Кнопка рядом с полем (поиск «Найти») может оставаться в одной строке с полем.
- Боковое поле страницы на телефоне (до 639 px) — одно на весь сайт, 16 px, как на главной и в каталоге: `.main-surface` (`padding: 32px 16px 72px`), `.catalog-surface`, закреплённая шапка поиска (`.search-pinned` выходит на те же −16 px), карточка напитка, цены и тирлисты. - Цель нажатия — не меньше 44×44 px; поля ввода на сенсорных экранах — 16 px (раздел «Стили»); ничего не должно вылезать за ширину экрана (проверяй `document.documentElement.scrollWidth` и правые края элементов).

## Стили

- Фото напитка в плитке каталога (карточка каталога, страница напитка, избранное, редактор тирлиста, карточка и мэтчи дейтинга — там у плитки с подложкой выключен `mix-blend-mode: multiply`, иначе он снова затемнил бы фон фото) — `CoverImage` (`cover-image.tsx`), а не голый `next/image`: после загрузки он рисует фото на canvas 32×32 и, если левый и правый края почти белые (`whiteBackdropColor` в `src/lib/cover-backdrop.ts`; верх и низ не считаются — высокая банка их касается), ставит плитке `data-backdrop="white"` и `--cover-backdrop` — средний цвет этих краёв (магазинный «белый» часто `#f5f5f5`). Тогда плитка (во всех тёмных темах она светло-серая) принимает цвет фона фото, и его фон не виден коробкой. Через ref, а не `onLoad`: next/image не вызывает `onLoad` для фото, загруженного до гидрации. Фото с другого домена без CORS не читается — плитка остаётся обычной. Ref — одна стабильная функция (`watchPhoto`): next/image перепривязывает ref, который меняется каждый рендер. Свои обложки (адрес с `/`: `/images/products`, `/brand/products`, фото участников) идут мимо оптимизатора (`unoptimized`): это JPEG 300 px по ~15 КБ, а оптимизатор Next читает исходник через соединение посетителя без таймаута — посетитель, отвалившийся на первой обработке фото, вешал этот адрес для всех до перезапуска (октябрь 2026, Tornado Black/Кокос/Boost). Тест: `test/cover-backdrop.test.ts`.
- Картинка в квадратной плитке, заданной через `aspect-ratio` (`.brand-collection-cover`, `.dating-match-cover`, `.story-pick-cover`), — `position: absolute; inset: 0; margin: auto` и проценты ширины/высоты: процентная высота внутри такого квадрата не считается, и высокое фото напитка участника растягивалось по своей высоте и обрезалось сверху.

- `src/app/globals.css` (корневой layout) блокирует первую отрисовку каждой страницы, поэтому в нём только общее: токены, базовые элементы, хедер, таб бар, футер, экран загрузки и всё, что рендерит главная. Стили одного раздела туда не добавляй.
- Стили разделов лежат в `src/styles/<раздел>.css`: `admin`, `auth` (`/sign-in`, `/auth/*`), `catalog`, `legal`, `market` (`/market/*` и `/messages/*`), `prices`, `profile`, `tierlists`. Правила, нужные нескольким разделам, но не главной, — в `src/styles/shared.css`. Каждый `page.tsx`/`error.tsx` раздела импортирует сначала `shared.css`, затем свой файл; новая страница раздела обязана импортировать оба.
- Файлы разделов грузятся после `globals.css`, поэтому при равной специфичности их правило побеждает глобальное, даже если в старом едином файле стояло выше. Часть правил разделов намеренно осталась в `globals.css`: они должны и дальше уступать более поздним глобальным правилам. Перенося правило, проверь, не перебьёт ли оно глобальное с той же специфичностью на том же элементе.
- Поля ввода (`input`, `textarea`, `select`) на сенсорных экранах — не меньше 16px: iOS Safari приближает страницу к полю мельче 16px при фокусе, и страница начинает ездить вбок. Мелкий шрифт поля на компьютере оставляй, а для телефона добавляй `@media (pointer: coarse) { … font-size: 1rem }` (так сделано у полей комментариев и записей, их правки, сортировки цен и форм магазина и напитка — `.store-form`). Поле, которое наследует размер от подписи (`font: inherit`), сканом CSS не найти — проверяй `getComputedStyle` в браузере.
- Next не выгружает CSS при клиентских переходах, и файлы разных разделов могут одновременно оказаться на странице. Селекторы раздела опирай на классы самого раздела, а не на общие (`h2`, `.community-button` без родителя). Порядок файлов после перехода тоже не гарантирован: `shared.css` может подгрузиться заново уже после файла раздела. Поэтому правило раздела для особого поля внутри `.store-form` (радиокнопка, тумблер, поле-чипсы) пиши сильнее общего `.store-form input:not([type=hidden])` (0,2,1): `.store-form .<свой класс> input:not([type=hidden])`. При равной силе после клиентского перехода радиокнопки сахара растягивались на всю ширину, а обновление страницы это «чинило».

## Производительность

- `profileRanking` — представление, которое при каждом обращении считает опыт и места всех участников. Не бери из него опыт подзапросом в строке (`(select xp from "profileRanking" where id = u.id)`): фильтр срабатывает после полного расчёта, и каждая строка ленты, отзывов, тирлистов или каталога пересчитывала рейтинг всего сайта (список 161 напитка стоил 734 мс). Опыт автора — `coalesce((select sum(points) from "profileExperience" where "userId" = u.id), 0)::int` (индекс `profileExperience_pkey`). Само представление — только для списков рейтинга, один раз на запрос.
- Аватарка в строке — подзапрос к `profileImage` по `("userId", kind)`, для него есть индекс `profile_image_user_kind` (миграция `0106`).
- Каталог на каждой странице берёт напитки участников лёгким запросом (`getPublishedDrinkIdentities`: id, бренд, вкус, название, `updatedAt`). Данные автора (`COLUMNS`) — только на странице напитка (`getCatalogDrink`, одна строка) и в админке.
- Клиентский кэш переходов: `experimental.staleTimes.dynamic = 30` в `next.config.ts` — страницы, открытые за последние 30 с, открываются без запроса к серверу; действия с `revalidatePath` его сбрасывают.
- Тяжёлые списки — частями: «Сообщество» показывает 12 тирлистов участников и «Показать ещё» (`more`, до 48), событие «оценил N напитков» в ленте кладёт в страницу не больше `REVIEWS_IN_FEED` (5) отзывов, остальные — по ссылке на отзывы автора.
- Фото и видео из базы кэшируются на устройстве (`src/lib/media-cache.ts`): под одним id файл никогда не меняется (новая аватарка, баннер или фото — новый id), поэтому аватарки, баннеры, фото отзывов, вложения стены и комментариев — `private, max-age=2592000, immutable` (30 дней), истории — час, фото опубликованного магазина — сутки, обложка напитка участника по адресу с версией — год. `private` — только на устройстве смотрящего, не в общих кэшах. Без кэша (`private, no-store`) — только то, что сейчас видят не все: заявки магазинов и напитков, вложения заказов маркета. Новый маршрут медиа — с тем же правилом; меняешь файл под тем же id — меняй и правило.
- Чтобы найти медленное место на проде без профилировщика: разница `pg_stat_user_tables` (`seq_scan`, `idx_scan`, `*_tup_*`) до и после одного запроса страницы показывает таблицы, которые она перебирает.

## Перезапуск при выкатке

- Перед сайтом — nginx на хосте VPS (`/etc/nginx/sites-available/canrush.ru`, копия в репозитории — `deploy/nginx/canrush.ru.conf`), а не Caddy: `Caddyfile` в compose не подключён. Upstream — `site` на `127.0.0.1:3002` и `backup` на `127.0.0.1:3003`.
- Сайт выкатывай скриптом `deploy/deploy-site.sh` (на VPS: `cd /opt/canrush && git pull && deploy/deploy-site.sh`), а не `docker compose up -d --build`: он собирает образ с номером коммита, прогоняет миграции, поднимает новый образ как `site-standby` на 3003 (профиль `standby`, воркеры Telegram и push выключены), пересоздаёт `site` и убирает запасной. Пока `site` перезапускается, nginx отдаёт страницы и действия с 3003 — без 502 и без ручной перезагрузки. В `proxy_next_upstream` только `error http_502`, без `timeout`: зависший ответ получает свой 504, а не повтор. Отказ в соединении значит, что запрос не ушёл, поэтому POST переносится безопасно. У `site` стоит `max_fails=0`: при `max_fails=1` одна ошибка выключала сайт на `fail_timeout`, и без запасного все страницы получали 502 на 3 секунды. Простаивающие keep-alive соединения nginx закрывает через 4 с (`keepalive_timeout` в `upstream`), а Node держит их 65 с (`KEEP_ALIVE_TIMEOUT` в `x-site-env`): иначе nginx иногда отправлял запрос в сокет, который Node только что закрыл (по умолчанию через 5 с), — «upstream prematurely closed connection», несколько раз в день. Конфиг на сервере — копия `deploy/nginx/canrush.ru.conf`; меняя его, копируй файл, `nginx -t`, `systemctl reload nginx`.
- Номер коммита — build arg `DEPLOYMENT_ID` → `NEXT_DEPLOYMENT_ID` → `deploymentId` в `next.config.ts`: открытая страница прошлой сборки сама перезагрузится при следующем переходе или действии, а не упадёт на исчезнувших файлах и server actions. Меняя переменные или тома сайта, правь общие якоря `x-site-env`/`x-site-volumes` в `docker-compose.yml` — их берут оба контейнера.

## Резервные копии

- Каждую ночь основной VPS делает зашифрованную копию базы и `.env` (03:30 МСК), резервный зарубежный VPS забирает её
  (05:00 МСК) и хранит 7 ежедневных, 4 еженедельных и 6 ежемесячных. Скрипты и порядок восстановления —
  `deploy/backup/vps/` (README там же). В `deploy/backup/` есть и старая схема на Яндекс Диск (rclone), но её
  systemd-таймер на сервере выключен. Копии шифруются на SSH-ключ владельца: без его закрытого ключа их не прочитать.
  Восстанавливать — в `postgres:16-alpine` или базу с сортировкой `C`, иначе не загрузится `profileCompatibilitySnapshot`.
  Ключ резервного VPS на основном может только `list`/`get` копий — не расширяй его права.
